Статус проекта tg_pool_framework

Что это

Фреймворк для управления пулом telegram-аккаунтов через Telethon: рассылки,
сбор пользователей (парсинг), проверка прокси, конвертация tdata<->session,
здоровье аккаунтов. Две части: питоновский бэкенд (можно запускать и как
консольную утилиту, и как REST API) и десктопный лаунчер на WPF, который
поднимает бэкенд локально и общается с ним по http+websocket.

Ниже — что реально готово по коду и тестам, а не по комментариям и не по
названиям файлов.


БЭКЕНД (Python)

Аккаунты (src/accounts)

Загрузка аккаунтов из папки, из tdata, из .session+.json пар, из переменных
окружения (до 49 слотов TG_API_ID_i/...). Раздача прокси по кругу на N
аккаунтов. Реестр аккаунтов в памяти с фильтрами/сортировкой (статус,
премиум, 2fa, страна, роль, папка, текстовый поиск), с опциональной
записью в БД. Health-check: логин, get_me, проверка 2FA, детект бана/
флуд-лимита, при deep_check — опрос @SpamBot с парсингом даты снятия
ограничения (RU/EN). Warmup-политика для новых аккаунтов (мягкий разгон
по дням). Шифрование .session файлов через Fernet. Два фоновых
шедулера — recheck по истечении cooldown и периодический recheck всего
пула.

Готово полностью, тесты есть на каждый файл.

API (src/api)

FastAPI-приложение. Эндпоинты: /health, /accounts (+role/folder/recheck/
rescan), /campaign (start/stop/status), /parsing (start/stop/status),
/proxy_check (start/status), /tdata_convert (start/status),
/session_convert (start/status), /ws/events (websocket с событиями по
аккаунтам/сообщениям/метрикам). Кампания и парсинг делят один и тот же
пул аккаунтов через PoolAccessGuard — второй не может стартовать, пока
работает первый.

Готово полностью, 44 теста на api, покрыты все эндпоинты и граничные
случаи (409 занято, 400 невалидный ввод и т.д.)

Рассылка — детально (src/messaging + orchestrator.py + api/campaign.py)

Это модуль, где было больше всего работы за последнее время. Реализовано
и покрыто тестами:

- спинтакс {вариант1|вариант2} в тексте, вложенность работает
- медиа: один файл или список (рандомный выбор на получателя), режимы
  video_note (кружочек) и voice (голосовое)
- репост существующего сообщения по ссылке (t.me/name/id и приватная
  t.me/c/id/id) или через бота-релей (юзернейм + список id постов,
  рандомный выбор)
- таргетинг по папке аккаунтов (account_folder) — кампания стартует
  только на аккаунтах с нужным тегом папки
- диапазон отправок на аккаунт (messages_per_account_min/max) — у
  каждого воркера случайная квота внутри диапазона, считаются только
  успешные отправки
- точное общее количество отправок (exact_total_target) — кампания
  крутит циклы, исключая уже отправленных получателей, пока не наберёт
  нужное число или пока источник не кончится
- отложенная отправка (schedule_at) — сообщение уходит через Telegram-
  планировщик, успех = "принято в очередь", не "доставлено"
- закреп после отправки (pin_after_send) — ошибка закрепления не рушит
  сам факт отправки
- запуск воркеров группами с паузой (worker_batch_size/delay) вместо
  одновременного старта всего пула
- повтор всей кампании через N часов (repeat_every_hours)

Плюс по мелочи: кнопки под сообщением ([Текст|url]), персонализация
{first_name}/{username} в тексте, адаптивный бэкофф при флуд-вейтах,
circuit breaker на воркера (после серии ошибок аккаунт временно
исключается, воркер переезжает на запасной), запись кампаний в БД.

Три вещи в это специально НЕ включены по моему отказу (обсуждали
отдельно) — авто-стоп по количеству банов, удаление диалогов для
сокрытия факта отправки, репост через одноразовый приватный чат на
аккаунт. Это осознанно не билдилось, не путать с "забыли".

Парсинг/сбор данных (src/extraction + orchestrator.py)

Стратегии сбора: участники группы, комментарии канала, сообщения
группы, реакции, опросы, системные сообщения, сообщения топика — все
реализованы по-настоящему (реальные вызовы Telethon, пагинация,
обработка FloodWait). Распределение источников по воркерам не round-
robin, а по весу (LPT — сначала оцениваем размер источника через
GetFullChannelRequest, потом жадно раскладываем по наименее загруженным
воркерам). Дедупликация между запусками через Redis (SADD + TTL).
Анти-флуд на источник через Redis rate limiter — но подключен только к
чисто парсинговому пайплайну (orchestrate_extraction_only), в рассылку
(orchestrate_multi_source) не прокинут. Выбор стратегии на источник
через Lua-скрипт (когда источников больше одного и стратегия не
зафиксирована явно). Экспорт в Excel (сводка/по источникам/полный),
с возможностью добавить кастомные колонки через Lua.

Готово полностью, тесты есть.

Прокси (src/proxy)

Проверка прокси написана с нуля, без внешних библиотек: реальный SOCKS5
handshake (с авторизацией), SOCKS4, HTTP CONNECT — каждый реально
стучится в дата-центр Telegram и меряет задержку. Гео по прокси —
офлайн-база (geoip2fast), без обращения к внешним сервисам. Конвертация
tdata<->session через opentele, батчами, с джиттером между аккаунтами,
с обработкой 2FA.

Готово, тесты есть.

Устойчивость и скрипты (src/resilience, src/scripting)

CircuitBreaker — стандартный CLOSED/OPEN/HALF_OPEN. LuaEngine —
песочница на lupa (вырезаны os/io/require/load, лимит памяти, лимит по
времени выполнения через хук на инструкции, hot-reload скриптов по
mtime). Используется для авто-ответчика, выбора стратегии парсинга,
кастомных колонок экспорта, фильтров пользователей.

Готово, тесты есть.

БД (src/db)

SQLAlchemy async, upsert через ON CONFLICT (postgres и sqlite). Три
линейные alembic-миграции: аккаунты -> кампании+результаты -> гео/2fa/
роль/папка. Всё это опционально — если DATABASE_URL не задан, всё
работает и без БД, просто без сохранения истории.

Готово.

CLI-режимы (src/features + main.py)

main.py выбирает режим по переменной MODE (или спрашивает интерактивно,
если запущено в терминале): send (рассылка), parse (парсинг),
check_accounts, check_proxies, convert_tdata, convert_session. Это
консольный аналог того же самого функционала, что и через API — файлы
почти зеркальны по логике.

Готово.


ЛАУНЧЕР (WPF)

Вкладки: Dashboard, Accounts, Campaign, ProxyCheck, RotationCheck,
Tdata, Parsing, Session->Tdata. Локализация на три языка (ru/en/zh),
переключается на лету без перезапуска.

Что готово полностью и вживую работает:
- Dashboard — статус подключения, live-статистика кампании, таблица
  аккаунтов по событиям с вебсокета
- Accounts — таблица, фильтры, пересканирование папки на новые аккаунты,
  recheck пула
- ProxyCheck — ввод списка, запуск проверки, таблица результатов
- Tdata и Session->Tdata — конвертация в обе стороны, с диалогами выбора
  папок
- Parsing — источники, стратегия, фильтры, экспорт, старт/стоп, прогресс

Кампания (Campaign) — тут главный разрыв. UI собирает и отправляет
только 5 полей из примерно 21, что умеет бэкенд: target, message,
media_path, buttons_raw, parse_mode. Всё остальное в интерфейсе
нарисовано (тумблеры, поля), но не подключено ни к чему — ни своего
DTO-поля, ни вызова в BackendClient. В коде это даже прямо
прокомментировано как временные заглушки. Не подключено:
media_paths (несколько файлов), media_kind (video_note/voice — тумблер
есть, эффекта нет), спинтакс (вообще не вынесен на экран), silent,
link_preview, forward_link и bot_relay (репост), account_folder
(таргетинг по папке), messages_per_account_min/max (поля есть,
задизейблены, зашиты 1/40), exact_total_target, schedule_at,
pin_after_send, worker_batch_size/delay, repeat_every_hours.

RotationCheck — вкладка целиком заглушка. У неё даже нет своего
эндпоинта на бэкенде: proxy_checker.py сейчас только меряет
доступность/задержку прокси, но не проверяет, какой IP реально
отдаётся через него. Кнопка Run задизейблена с пояснением почему.

Мелкие незавершённости в Accounts — 5 иконок в колонке действий
(папка/юзернейм/2FA/инфо/монитор) нарисованы, но не привязаны ни к
одной команде. Методы AssignRoleAsync/AssignFolderAsync в
BackendClient есть и работают, просто их никто не вызывает из
интерфейса.

Автообновления в лаунчере нет — ни механизма проверки версий, ни
самого апдейтера.


ИНСТАЛЛЯТОР (installer/)

Inno Setup. Ставит портативно (Program Files или папка пользователя —
можно без прав администратора), кладёт рядом самодостаточный exe
лаунчера и исходники бэкенда (без скомпилированного питона внутри —
питон должен быть установлен на машине пользователя отдельно). Создаёт
структуру Data\ (аккаунты, прокси, экспорты, логи, крэши) с нужными
правами. Проверяет наличие python в PATH, если есть — сам ставит
зависимости из requirements.txt, если нет — показывает сообщение с
просьбой поставить питон вручную. Апдейтера тоже нет.
